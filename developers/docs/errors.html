Errors and idempotency

Two kinds of answer. A decision you did not want is a 200 with a response code. A request the network could not process is a 4xx or 5xx with a type and a message.

Before you startAn answer you did not expect and its request_id, from your own logs or from Logs in the Developer Portal.

Idempotency

Send an Idempotency-Key header on any POST. Repeat the same key within 24 hours and you get the original answer, not a second authorization. One key per attempt on your side. A key still in flight returns 409: wait for the first answer, do not retry during it.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/authorizations \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7" \
  -d @request.json
// the library sets a key per call; pass your own to make a retry safe
await dgn.authorizations.create(body, { idempotencyKey: order.id + ":auth" });
client.authorizations.create(**body, idempotency_key=f"{order.id}:auth")

When to retry

Retry, same keynetwork_error, rate_limited after Retry-After, a timeout with no answer.
Retry, new messageA soft decline, 51, on your own schedule. Never within 60 seconds.
Do not retryinvalid_request, unauthorized, forbidden, a hard decline: 05, 14, 54.
Waitconflict, 409. The first request is still in flight.

Rate limits

5,000 requests a minute per key in production, 500 in the sandbox. Over the limit returns 429 with Retry-After in seconds. Limits are on the key, so one key per service keeps a noisy service from starving another.
