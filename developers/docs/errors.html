Errors and idempotency

Two kinds of answer. A decision you did not want is a 200 with a response code. A request the network could not process is a 4xx or 5xx with a type and a message.

Before you startAn answer you did not expect and its request_id, from your own logs or from Logs in the Developer Portal.

Which kind of answer

The HTTP status says which table to read. A 200 carries a decision, and response_code is the issuer's word. Anything else carries an error, and type is the network's word.

A decision200
{
  "id": "auth_71ab52",
  "decision": "declined",
  "response_code": "51",
  "reason": "insufficient_funds",
  "request_id": "req_71ab52"
}
Read response_code under Response codes.
An error400
{
  "type": "invalid_request",
  "message": "amount must be a positive integer in minor units",
  "param": "amount",
  "request_id": "req_71ab00"
}
Read type under Error types. Quote request_id to support.

Idempotency

Send an Idempotency-Key header on any POST. The network authorizes once and keeps the answer under that key for 24 hours. A repeat with the same key gets the original answer. A repeat while the first request is still in flight gets a 409.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/authorizations \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7" \
  -d @request.json
// the library sets a key per call. Pass your own so a retry is the same attempt.
await dgn.authorizations.create(body, { idempotencyKey: order.id + ":auth" });
client.authorizations.create(**body, idempotency_key=f"{order.id}:auth")
