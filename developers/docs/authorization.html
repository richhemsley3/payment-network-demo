How a payment moves

Four calls and two events carry a payment from the terminal to the wire. Your host makes the calls. The network answers each one and sends the events.

Authorize

An authorization asks the issuer to hold an amount. The answer is a decision, the issuer's code, and how long the issuer took.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/authorizations \
  -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
  -d '{ "amount": 5820, "currency": "USD", "merchant_id": "mch_demo", "pan_token": "tok_9d1b4e", "entry_mode": "ecommerce", "avs": { "street": "12 Ash St", "postal": "80202" } }'
const auth = await dgn.authorizations.create({ amount: 5820, currency: "USD", merchantId: "mch_demo", panToken: "tok_9d1b4e", entryMode: "ecommerce", avs: { street: "12 Ash St", postal: "80202" } });
auth = client.authorizations.create(amount=5820, currency="USD", merchant_id="mch_demo", pan_token="tok_9d1b4e", entry_mode="ecommerce", avs={"street": "12 Ash St", "postal": "80202"})

The four answers

Every authorization answers with one of four decisions. The code says why, and answered_by says who.

decisionCodeanswered_byWhat you do
approved00issuerCapture within 7 days.
partial10issuerA prepaid or limited card approved less than requested. Capture approved_amount, or reverse and ask for another card.
declined51 05 14 54issuerRead the code. Every code says whether a retry is allowed.
stand_in00networkThe issuer did not answer within 500 ms. Your stand-in rules answered, inside the ceiling per transaction and per card per day set in Configuration. Capture like any other approval.

Where an authorization can go

An approval is a hold. What you call next moves it, and the night's cycle moves it without you.

StateWhat moves it thereWindow
authorizedThe issuer, or stand-in, approved the hold.7 days before the hold lapses
capturedYou called Capture. The amount joins the day's clearing file.Within 7 days of the authorization
settledThe night's cycle posted. settlement.posted carries the wire reference.About 6:00 AM ET the next day
reversedYou called Reverse before capture. The issuer releases the hold at once.Any time before capture
refundedYou called Refund after capture. The cardholder sees the money in 3 to 5 days.Any time after capture
disputedThe cardholder's bank opened a case. dispute.opened carries the reason code and your evidence deadline.Up to 120 days after settlement

Capture

Move an approved hold into the day's clearing file. A batch takes up to 5,000 ids on one call.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/captures \
  -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
  -d '{ "authorization_id": "auth_71ab3c", "amount": 5820 }'
await dgn.captures.create({ authorizationId: "auth_71ab3c", amount: 5820 });
// end of day
await dgn.captures.createBatch({ authorizationIds: ids });
client.captures.create(authorization_id="auth_71ab3c", amount=5820)
client.captures.create_batch(authorization_ids=ids)

Reverse

Release a hold you no longer need, in full or in part. The issuer sees it immediately.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/authorizations/auth_71ab3c/reverse \
  -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
  -d '{ "amount": 5820 }'
await dgn.authorizations.reverse("auth_71ab3c", { amount: 5820 });
client.authorizations.reverse("auth_71ab3c", amount=5820)
Response200

  "status": "reversed",
  "released_amount": 5820,
  "held_amount": 0,

Refund

Return captured money to the cardholder, in full or in part. It reaches the cardholder in 3 to 5 days and appears in that night's cycle as an adjustment.

curl -X POST https://sandbox.api.dgn.com/acceptance/v1/refunds \
  -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
  -d '{ "authorization_id": "auth_71ab3c", "amount": 2000, "reason": "requested_by_customer" }'
await dgn.refunds.create({ authorizationId: "auth_71ab3c", amount: 2000, reason: "requested_by_customer" });
client.refunds.create(authorization_id="auth_71ab3c", amount=2000, reason="requested_by_customer")

The score

Every authorization response carries score, 0 to 100, and score_reasons: network-side signal the issuer does not hold. Read it or ignore it. Rules on it live in Fraud in the Partner Portal.

ReasonWhat the network sawMoves the score
device_seen_beforeThis device has paid this merchant before.down
velocitySeveral cards from one device inside twenty minutes.up
avs_mismatchThe street or the postal code did not match.up
merchant_baselineThe merchant is outside its own fourteen-day baseline.up
